Perform a complete audit of this AI language trainer app. Go through every
category below, report findings as PASS / WARN / FAIL with the specific file
and line, and propose a fix for each FAIL or WARN. Do not change code yet —
audit first, then list fixes in priority order.

1. SECURITY (highest priority)
- Is the Anthropic API key exposed anywhere client-side? Check the HTML/JS for
  hardcoded keys, keys in fetch headers, or keys pulled from a public variable.
- If the app calls api.anthropic.com directly from the browser, flag it: the key
  is visible to any user. Recommend a backend proxy / serverless route and
  Replit Secrets instead of inline keys.
- Check for any other secrets, tokens, or endpoints committed in the code.
- Review CORS, and whether requests can be abused/spammed (rate limiting).

2. ANTHROPIC API USAGE
- Confirm the model string is current and valid, and max_tokens is set sensibly.
- Check error handling: network failure, 401, 429 (rate limit), 529 (overloaded),
  and malformed responses. Does the UI degrade gracefully or just break silently?
- Is conversation history sent correctly each turn (the API is stateless)?
- Are responses parsed by content-block type, not by array position?

3. WEB SPEECH API (speech recognition + synthesis)
- Check browser support detection and the fallback when SpeechRecognition or
  speechSynthesis is unavailable (e.g. Firefox, some mobile browsers).
- Verify microphone permission handling and the prompt shown if denied.
- Test continuous vs single-shot recognition, interim results, and language/accent
  config (en-GB vs en-US).
- Check that recognition stops cleanly and doesn't leak listeners or double-fire.
- Verify TTS voice selection, rate/pitch, and behaviour if no voice is loaded yet.

4. FUNCTIONALITY & STATE
- Trace the full conversation loop: speak → transcribe → send → respond → speak.
- Identify race conditions (e.g. user speaks while TTS is still playing).
- Check state resets, restart behaviour, and any memory leaks over a long session.

5. UX & ACCESSIBILITY
- Loading / "thinking" indicators while waiting on the API.
- Clear visual state for listening / speaking / idle.
- Keyboard fallback for users who can't or won't use voice.
- Contrast, focus states, and aria labels on interactive controls.

6. MOBILE & CROSS-BROWSER
- Test layout and speech features on mobile Safari and Chrome Android.
- Flag anything that only works on desktop Chrome.

7. CODE QUALITY
- Dead code, duplicated logic, magic numbers, and missing comments on the
  speech/API plumbing.
- Any console errors or warnings on load and during a full interaction.

Output: a findings table, then a prioritised fix list (Critical → Nice-to-have),
then ask me which fixes to apply before touching any code.
